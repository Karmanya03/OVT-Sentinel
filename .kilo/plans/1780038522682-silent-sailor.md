# Plan: Agentic Terminal Execution via `/chat`

## Goal
Make the `/chat` Discord command (and related thread/mention chat flows) able to run commands on a connected Sentinel VM **only when an agent is connected**, executing them agentically through the LLM's tool-use loop.

## Current State
- `llm_brain.chat()` supports tool use when `config.use_agent_tools` is globally enabled.
- `session_cog.chat()` and `on_message` call `llm.chat()` without any awareness of whether a VM agent is actually connected.
- The tools in `core/tools.py` (`run_bash_command`, `run_ovt_command`, etc.) already talk to the agent, but they depend on a context-var user set inside `llm_brain.chat()`.
- There is no per-request toggle for tool availability; it is purely global config.
- `run_bash_command` has a docstring claiming support for pipes/chaining/redirects, but `_sanitize_shell` actually blocks `|`, `&&`, `;`, `>` etc. This is a latent bug that blocks "any command" execution.

## Changes

### 1. `sentinel-bot/core/llm_brain.py`
- Update `chat()` signature to accept an optional `enable_tools: Optional[bool] = None`.
  - `None` defaults to `self.config.use_agent_tools`.
  - `False` disables tool setup for that call.
- Pass the flag down through:
  - `_chat_gemini(..., use_tools: bool)` – when `False`, pass `tools=None` and `tool_map=None`.
  - `_chat_mistral(..., use_tools: bool)` – when `False`, pass `tools=None`.
  - `_chat_langchain(..., use_tools: bool)` – when `False`, bypass LangChain agent creation and call `llm.ainvoke` directly.
- Keep `set_tool_user_context` behaviour **only** when `enable_tools` is truthy, so no user context leakage on plain chat.
- Update `analyze_output()` to explicitly pass `enable_tools=False` to prevent analysis loops from accidentally triggering new commands.

### 2. `sentinel-bot/bot/cogs/session_cog.py`
- In `chat()` (slash command):
  1. Detect if the user has a connected agent:
     ```python
     agent = await self.agent_manager.get_agent(str(interaction.user.id))
     has_connected_vm = agent is not None and agent.is_connected
     ```
  2. Call `self.llm.chat(..., enable_tools=has_connected_vm)`.
- In `on_message`:
  1. Same check against `message.author.id`.
  2. Call `self.llm.chat(..., enable_tools=has_connected_vm)`.

### 3. `sentinel-bot/core/tools.py`
- Fix `_sanitize_shell` to correctly allow pipes (`|`), chaining (`&&`, `;`), redirects (`>`), and other standard shell syntax that `run_bash_command` advertises.
  - Keep blocking command substitution (`$(...)`, `${...}`, backticks) and excessively long commands.
  - Consider adding a confirmation gate only when truly destructive system patterns are detected (already handled by `_is_destructive_system`).
- No new tools are needed because `run_bash_command` and `run_ovt_command` already cover terminal commands.

### 4. Backwards Compatibility
- Existing `/run`, `/stream`, and other cogs remain untouched.
- `llm_brain.analyze_output()` and other callers of `chat()` continue to work because `enable_tools` defaults to the global config.

## Files to Modify
1. `sentinel-bot/core/llm_brain.py`
2. `sentinel-bot/bot/cogs/session_cog.py`
3. `sentinel-bot/core/tools.py`

## Nice-to-have (out of scope for this plan)
- A transient in-chat confirmation flow for destructive commands mid-turn (user can still reply "yes" and the LLM will see the tool result on the next turn via existing history).
- Explicit message to the user when tools are enabled/disabled (e.g. a small footer or reaction).

## Risks & Mitigations
| Risk | Mitigation |
|------|------------|
| LLM tries to call a tool while agent is offline | We explicitly pass `enable_tools=False` when the agent is not connected, so the model never receives tool definitions on that turn. |
| Destructive commands executed without confirmation | Existing tool guards in `tools.py` (`_is_destructive`, confirmation prompts) remain active and return a refusal that the LLM surfaces to the user. |
| Sanitization blocking legitimate bash syntax | `_sanitize_shell` will be fixed to match the tool's documented capabilities; only truly dangerous patterns (command substitution, raw rm -rf /, etc.) will be blocked. |
